# 《喵都幸存者》微信小游戏化方案

> 撰写日期：2026-09-08 · 基于 H5 版本（js/main.js @ 20260908d）
> 定位：技术评审 + 立项会展评用。平台限制类数据均标注复核要求，执行前以官方最新文档为准。

---

## 1. 目标与结论先行

**推荐路径：以微信小游戏为主平台改造，H5 网页版继续保留作为「即开即玩」入口；跑通后 QQ 小游戏（复用度约 90%）、抖音小游戏（约 85%）作为第二、三站。**

总体可行性判断：**高**。本项目几乎是理想的小游戏化候选：

| 维度 | 现状 | 对小游戏化的意义 |
|---|---|---|
| 美术资源 | 100% 程序化 Canvas 绘制，无图片文件 | 包体极小，无图集/压缩纹理工作 |
| 音乐音效 | 全部 WebAudio 实时合成，无音频文件（除猫叫采样） | 包体极小；仅需适配 wx 的 WebAudio 实现 |
| 输入 | 触摸虚拟摇杆已实现，单指操作 | wx.onTouchStart 几乎零成本迁移 |
| 渲染 | 单主 canvas + requestAnimationFrame，dpr≤2 | 与小游戏渲染模型同构 |
| 包体 | JS 约 428KB（未压缩）+ 猫叫采样约 430KB | 远低于主包 4MB 上限，无需分包 |
| 主要改造点 | DOM 覆盖层 UI（菜单/三选一/结算等）依赖 HTML/CSS | **这是最大的改造量**，需重写为 Canvas UI |

预计单人投入 **15～23 人日**（详见第 7 节路线图）。合规侧（实名/防沉迷/备案）由平台托管为主，但软著等提审材料存在办理周期，建议与开发并行启动。

## 2. 平台差异盘点

微信小游戏**没有浏览器 DOM/BOM**：没有 `document`、`window`、HTML 元素、CSS，只有一个纯 JS 运行环境 + `wx` API + Canvas。以下逐项对照现有代码。

### 2.1 入口形态

| H5 现状 | 小游戏对应 |
|---|---|
| index.html + 10 个 `<script>` 标签顺序加载 | `game.js` 单入口（可用 require/ES Module 组织） |
| viewport meta / CSS 布局 | `game.json` 声明屏幕方向等全局配置 |
| GitHub Pages 静态部署 | 微信开发者工具上传、平台托管 |

`game.json` 关键配置（字段名以官方最新文档为准）：

```json
{
  "deviceOrientation": "landscape",
  "showStatusBar": false,
  "openDataContext": "openDataContext"
}
```

- `deviceOrientation`：本游戏方向自适应，两种都可。**建议横屏**（幸存者like 视野更宽，摇杆在左手位更顺）；若选竖屏则锁定 portrait，避免半屏切换。
- `openDataContext`：好友排行榜开放数据域目录，见第 6 节。

### 2.2 Canvas

- 主画布：`wx.createCanvas()` **第一次调用**返回上屏主 canvas，之后调用全部返回**离屏 canvas**——这是移植时最经典的坑。适配层应把首次调用结果缓存为全局主 canvas，业务代码不允许再裸调 `wx.createCanvas()`。
- 本项目有大量离屏 canvas 用法（chunkCache 地图块缓存、vignette、菜单立绘、卡牌图标、战报图）。**离屏 canvas 数量有平台上限且不自动回收（以官方文档为准）**：`chunkCache` 必须加 LRU 上限（如 24 块）并主动销毁；小尺寸临时 canvas（卡牌图标）可复用池。

### 2.3 浏览器 API 依赖 → 小游戏方案（适配层清单）

| 现有依赖（出处） | 小游戏方案 |
|---|---|
| `document.getElementById('game')` + `getContext('2d')`（main.js:10） | `wx.createCanvas()` 首次调用；`getContext('2d')` 可用 |
| `window.devicePixelRatio / innerWidth / innerHeight`（main.js:15-16） | `wx.getWindowInfo()`（旧 API `wx.getSystemInfoSync()`，建议两层兜底），取 `pixelRatio / windowWidth / windowHeight` |
| `window.addEventListener('resize' / 'orientationchange')`（main.js:35-38） | `wx.onWindowResize()`；横竖屏锁定后事件减少，保留帧循环内自检兜底逻辑 |
| `cv.addEventListener('touchstart/move/end/cancel')`（main.js:233-257） | `wx.onTouchStart/Move/End/Cancel`，事件对象同样含 `touches[i].clientX/Y`，虚拟摇杆逻辑几乎原样迁移 |
| `window.addEventListener('keydown/keyup')`（main.js:222-229） | 移动端不需要；PC 端微信小游戏有键盘 API（可选，以官方文档为准），先移除 |
| `window.addEventListener('blur')`、`document.visibilitychange`（main.js:2906-2907） | `wx.onHide()`（自动暂停）、`wx.onShow()`（恢复） |
| `requestAnimationFrame`（main.js:2912） | 小游戏全局原生提供，直接沿用 |
| `performance.now()`（main.js:204/861 等） | 环境**不保证**存在；适配层 shim：`performance.now || Date.now`，或 `wx.getPerformance()` |
| `localStorage`（util.js:42-50，键：meow_best / meow_best_mother / meow_map / 已读日志版本） | `wx.getStorageSync / setStorageSync`（容量远大于需求，以官方文档为准）；util.js 的 storage 对象内部换实现即可，业务零改动 |
| `fetch('assets/meow/xx.mp3') + arrayBuffer`（audio.js:159-165） | 包内资源不走 HTTP：`wx.getFileSystemManager().readFile()` 读包内相对路径得 ArrayBuffer，再交给 `decodeAudioData` |
| `window.AudioContext / webkitAudioContext`（audio.js:9） | `wx.createWebAudioContext()`（基础库 2.19.0+），详见 2.4 |
| `new Image()` | `wx.createImage()`（本项目美术全程序化，基本用不到，适配层保留即可） |
| `location.search`（dev/auto 参数，main.js:5-6） | 小游戏无 URL query：用 `wx.getAccountInfoSync().miniProgram.envVersion`（develop/trial/release）替代 dev 判定 |
| `document.createElement('div/button/canvas')` + classList + CSS（main.js UI 段约 1000+ 行） | **无替代 API，需重写为 Canvas 绘制 UI** + `wx.onTouch` 命中检测，见 2.5 |
| `<a download>` 导出配置 / 战报 PNG（config_panel.js:303、result.js:275） | `wx.canvasToTempFilePath()` → `wx.saveImageToPhotosAlbum()`（战报保存）；⚙平衡设置面板为开发工具，小游戏包建议直接剔除 |
| 自动错误浮层 `window.addEventListener('error')` | 移除，改用平台后台 vConsole / 体验版调试 |

### 2.4 音频：WebAudio 在微信小游戏的可用性

现有 `js/audio.js` 用到的节点：Oscillator、Gain、BiquadFilter、Delay、DynamicsCompressor、BufferSource、decodeAudioData、噪声 Buffer。

- 微信提供 `wx.createWebAudioContext()`，接口形态与标准 WebAudio 一致；**但各节点（尤其 DynamicsCompressor、Delay）在部分基础库/机型的支持度需逐个验证（以官方文档与真机实测为准）**。
- 迁移策略：保留 audio.js 的合成器代码不动，只把 `ensure()` 里的上下文创建换成适配层，并在初始化时**逐节点探测**，缺失时按序降级：
  1. 缺 Compressor → 直连 master（仅影响响度一致性）；
  2. 缺 Delay → 关闭回声 send；
  3. WebAudio 整体不可用（极老机型）→ BGM/音效整体静默 + 仅用 InnerAudioContext 播猫叫采样，保证可玩。
- 用户手势解锁：H5 用首次触摸 resume；小游戏同样需要首次 `wx.onTouchStart` 后 `ctx.resume()`，现有 `onAnyInput` 钩子可直接挂上。
- `InnerAudioContext`（`wx.createInnerAudioContext()`）：直接播包内 mp3 路径，实现最简单但**启动延迟较高、不适合高频音效**；适合作为采样喵叫的备选通道（喵叫本身有 2.5s 防密集冷却，低频事件，延迟可接受）。

### 2.5 UI 重写：DOM 覆盖层 → Canvas UI

index.html 约 380 行 CSS + DOM 结构，对应 6 个屏幕：主菜单（地图选择）、玩法说明、更新日志、升级三选一、宝箱、暂停、结算（含构筑清单）、平衡设置。改造方案：

- 写一个极简 Canvas UI 层：面板圆角/描边/按钮/文字布局全部 `ctx` 绘制（项目已有一套奶油色系配色常量可平移），触摸命中检测用矩形/圆形区域表。
- 升级三选一、结算构筑 chips 等动态 UI 由数据驱动渲染，逻辑分支（hidden/按钮回调）保持原有流程函数不变，只换「渲染 + 点击」两端。
- 更新日志面板（changelog.js 数据可复用）、玩法说明为纯文本滚动列表，Canvas 排版工作量小。
- ⚙平衡设置面板**建议小游戏包剔除**（其导出功能依赖浏览器下载，且属于开发向工具，正式平台无意义）。

### 2.6 字体

Google Fonts 在线加载（index.html:9）在小游戏内**不可用**（无网络字体机制；且审核环境禁止运行时拉取代码类资源）。方案对比：

| 方案 | 做法 | 体积 | 优劣 |
|---|---|---|---|
| A. 系统字体栈（推荐兜底） | canvas font 串改为 `"PingFang SC","Microsoft YaHei",sans-serif` | 0 | 零成本；失去 ZCOOL 快乐体的萌系标题感 |
| B. 子集化内置字体（推荐主案） | ZCOOL KuaiLe 为 OFL 开源协议可随包分发；用 fonttools 等工具按游戏实际用字做子集（估计数百字符），`wx.loadFont()` 加载 | 约 50～200KB | 保留美术风格；`wx.loadFont` 对 ttf/woff 支持与失败静默返回 null 的行为需真机验证（以官方文档为准），失败自动落 A |
| C. 标题预渲染贴图 | 仅标题等少量美术字离屏 canvas 预渲染 | 极小 | 只解决标题，正文仍需 A/B，作为 B 的补充 |

建议 **B + A 兜底**：game_config/武器名等游戏内文案字符集封闭，子集一次即可；新增文案时需重新生成子集（列入发版 checklist）。result.js 里硬编码的 `FONT` 常量收敛到适配层统一管理。

### 2.7 猫叫 mp3 采样（assets/meow/，22 个约 430KB）

- 体积：430KB 全量入主包毫无压力（见第 3 节），**无需分包**。
- 加载策略：H5 版是「页面加载即 fetch 预取、首次解锁后解码」。小游戏版改为：首局加载期后台 `readFile` 预取 → 首次触摸解锁后 `decodeAudioData`；未就绪时沿用现有合成喵叫兜底（audio.js 已内建该降级，逻辑零改动）。
- 版权：CREDITS.md 所列各采样协议必须随包保留并在审核材料中说明来源授权。

## 3. 包体与资源策略

| 项 | 数值 | 备注 |
|---|---|---|
| 本项目 JS（未压缩） | ~428KB | 10 个文件；压缩混淆后预计 ~200KB |
| 猫叫采样 | ~430KB（22 个 mp3） | 全量入包 |
| 字体子集（方案 B） | ~50～200KB | 可选 |
| **合计** | **< 1.1MB** | |
| 微信小游戏主包上限 | 4MB | 常见口径，**以官方最新文档为准** |
| 微信小游戏整包上限（主包+分包） | 20～30MB（平台多次上调过） | **以官方最新文档为准** |

结论：**包体不构成任何约束**，不需要分包、不需要 CDN 资源、不需要引擎裁剪。仍保留两条纪律：

1. 采样若未来扩充，先做裁剪（截去尾部长静音）与转码（单声道、48～64kbps、22.05kHz，猫叫对高频损失不敏感），单文件可压到 5～15KB；
2. 禁止把 H5 侧无关文件（shots\$m.png、preview/、lab/、tools/）带进小游戏包目录，用独立 `minigame/` 构建目录 + 复制脚本圈定白名单。

## 4. 性能与分辨率 / DPI

| 项 | 现状 | 小游戏方案 |
|---|---|---|
| 像素比 | `dpr = min(2, devicePixelRatio)`（main.js:15） | 沿用：`min(2, wx.getWindowInfo().pixelRatio)`；低端机（见下）降到 1.5 或 1 |
| 视口 | innerWidth/Height + 每帧自检 | windowWidth/Height + `wx.onWindowResize`，保留帧循环自愈检查 |
| 帧率目标 | rAF 满帧（60fps） | 中端机 60fps；帧循环加 2s 滑动窗口采样，低于 ~45fps 持续时依次触发：dpr 降档 → 关震屏/粒子 → dpr=1 |
| 同屏实体上限 | 敌人 capBase 38 → capMax 265；投射物 480；鱼干 gemMax 330（game_config.js:58-61/272/394） | 直接沿用，Canvas 2D 在该量级无压力；上限已是性能保护设计，无需重调 |
| 世界缩放 | 小屏 zoom 0.35～0.5 自适应（main.js:21） | 原样沿用 |
| 内存 | chunkCache 无上限（H5 靠浏览器 GC） | **必须改**：LRU 上限 + 离屏 canvas 主动销毁；`wx.onMemoryWarning()` 注册回调时同步清缓存 |
| 后台切换 | blur/visibilitychange 暂停 | wx.onHide 暂停（BGM 停、rAF 由平台挂起），wx.onShow 恢复 |

验收基线：iPhone 中端机型与 1500 元档安卓机各一台，15 分钟一局（含第 3 轮老鼠妈妈战）满帧或近满帧、无明显发热降频、无崩溃。

```

├── game.js               # 入口：初始化适配层 → 启动主程序

│   ├── wechat.js         # wx.* 实现：canvas/触摸/存储/系统信息/文件
```

| **P3 提审上线** | 发布 | 体验版全设备回归；包体/类目/材料提交；审核意见跟进；正式发布 + 数据监控 | 2～4 人日（不含软著等审批等待） | 过审发布；线上崩溃率/启动耗时达标 |

合计 **15～23 人日**。长期双端维护策略：游戏逻辑与数值收敛在 src/（与 H5 单一来源），平台差异全部关进 platform/，发版 checklist 加入「字体子集重生成 + 双端同步验收」。

## 9. 备选方案对比

## 10. 结论

**值得做。** 本项目「零图片 + 全合成音频 + 程序化地图」的资源形态天然契合小游戏包体模型，核心玩法代码复用度高，最大的工作量（DOM UI → Canvas UI）是一次性成本且不改变玩法逻辑。微信小游戏是目前国内单机休闲游戏分发成本最低的正规渠道，且无内购路径暂时绕开版号硬门槛。

1. 立项当天启动**软著申请**（周期最长，决定上线日历）；
2. P0 用 6～9 人日把最小可玩版跑上真机，重点验证 wx WebAudio 与离屏 canvas 两个技术疑点；
3. P0 验证通过后再投入 P1/P2 的完整体验与社交功能，避免在技术疑点落定前过度开发。
