# 手机端分辨率与 UI 规格方案（喵都幸存者）

> 2026-09-09 · 基于 iPhone 16 Pro（横屏 874×402pt @3x，dpr 截到 2 → 画布 1748×804）
> 与两款竖屏同类小游戏截图（890×1999，约 2.21 图像px = 1 逻辑pt）的实测对照。
> 本文档只定规格，不改代码；实施时按「变换清单」逐条执行。

## 1. 分辨率现状

| 项 | 数值 |
|---|---|
| 设计基准 | 1280×720（16:9 横屏，桌面浏览器窗口） |
| 画布机制 | 逻辑分辨率自适应：cv.width = vw×dpr，dpr 上限 2 |
| 世界缩放 | zoom = clamp(短边/2000, 0.35, 0.5) —— 短边 <700 一律按 0.35 |
| 字号单位 | 两套混用：主菜单/面板 = vh 百分比；HUD/飘字/地图瓦片 = 固定 px（按 720p 调） |

典型小游戏逻辑分辨率（点/pt，非物理像素）：

| 设备 | 竖屏 | 横屏（本游戏） |
|---|---|---|
| iPhone 16 Pro | 402×874 | **874×402**（2.17:1） |
| iPhone SE/小屏安卓 | 375×667 | 667×375（1.78:1） |
| 主流安卓 | 360~412×780~932 | 780~932×360~412（2.05~2.22:1） |
| iPad | 820×1180 | 1180×820（1.44:1） |

结论：设计基准 720 短边 ≈ 桌面窗口；**真机横屏短边只有 ~400pt**，是基准的 0.56 倍。

## 2. 参考游戏实测（同类竞品，可读性基准）

换算：图像px ÷ 2.21 = 逻辑pt。

| 元素 | 图像px | 逻辑pt | 占短边(402) |
|---|---|---|---|
| 面板大标题（技能选择） | ≈60 | ≈27pt | 6.7%h |
| 卡片技能名 | ≈32 | ≈14.5pt | 3.6%h |
| 卡片描述正文 | ≈24-26 | **≈11-12pt** | 2.7-3.0%h |
| 提示行（从上方选择…） | ≈34 | ≈15pt | 3.7%h |
| 计时器 | ≈48-55 | ≈22-25pt | 5.5-6.2%h |
| 计数器（金币/击杀） | ≈26-30 | ≈12-14pt | 3.0-3.5%h |
| 伤害飘字 | ≈22-28 | ≈10-13pt | 2.5-3.2%h |
| 经验宝石 | ≈20-22 | ≈9-10pt | 2.2-2.5%w |
| 敌人（宽） | ≈55-75 | ≈25-34pt | **6.2-8.5%w** |
| 玩家（宽） | ≈50-70 | ≈23-32pt | 5.7-8.0%w |

**规律**：手机上最小可读字号 ≈ 11pt（短边 2.7%）；舒适正文 12-14pt；大标题 22-30pt；
角色宽 = 短边 6-8.5%；玩家周围同屏敌人可见 15-30 只（视野半径 ≈ 屏宽 0.5-0.7 倍世界距离）。

## 3. 我们在真机上走样的根因

1. **设计短边假设失效**：zoom 公式把短边 <700 一律钳到 0.35。手机短边 402 → 期望 0.2，被钳成 0.35。
   结果：角色 96px×0.35 ≈ 34pt = 屏高 **8.4%**（桌面 720p 下是 4.7%）——全局放大 ~1.76 倍，
   视野相应变窄（同屏敌人变少、走位空间变小）。
2. **固定 px 的 HUD/瓦片**：计时器 34px、飘字 15/22px、地图瓦片 92×69、猫砂提示 12px……
   都按 720p 调的绝对值，在 402 短边上相对放大约 1.76 倍（计时器占屏高 4.7%→8.5%）。
3. **长宽比 2.17 vs 设计 1.78**：vh 相对的元素比例虽守恒，但 vw 方向被拉宽，
   首页「标题/猫/地图格/按钮」四块的相对比重全部改变——这是"首页和设计不一样"的第二成因。
4. **横屏未生效的机型风险**：若真机上未旋转（个别安卓+系统旋转锁），vw/vh 互换，
   菜单会完全错位（地图格与猫、按钮大面积重叠）。**先在手机上确认显示方向**，
   这是"完全不一样" vs "比例不对"的分水岭。

## 4. 调整方案

### ★ v3 最终方案（2026-09-09 定稿）：虚拟视口，替代 v2 逐元素缩放

**机制（全部实现在 adapter.js，~30 行；ui.js 可选 ~10 行；transform 零新增规则；网页版零改动）：**

```
物理屏：874×402pt（横屏 iPhone16Pro）
        │  adapter 启动时给游戏上报一个「虚拟视口」：
游戏看到：VH = 720（常量，= 设计基准短边）
          VW = round(720 × 物理宽高比)    // 874/402=2.174 → 1565
          devicePixelRatio = 物理画布宽/VW // 1748/1565 ≈ 1.12
        │  触摸：物理pt → 虚拟px 反线性映射（×VW/874, ×720/402）
        │  胶囊/安全区：物理 rect → 虚拟坐标
游戏照旧读 window.innerWidth/innerHeight/devicePixelRatio —— 拿到的全是虚拟值，
内核（含未来网页版更新的全部逻辑）对缩放零感知。
```

- **首页/面板/HUD**：按桌面 720p 的比例 1:1 重现（vh 相对项与设计完全一致），多出的屏幕宽度
  成为左右留白/更多横向视野；ui.js 可把首页内容钳制在 min(vw,1280) 虚拟宽内，复刻设计稿版式。
- **世界视野**：zoom = 720/2000 = 0.36（与桌面同值），横向视野比桌面宽 22%（2.17:1 的加成）。
- **文字物理大小**：15px 飘字 → 8.4pt（1.4mm@持机25cm，角尺寸≈桌面 0.4m 处观感），解决"文字太大"。
- **唯一可调参数**：VH。720=完全桌面观感；真机上若觉得文字偏小，改 640/600 一档全体放大，一个数字重验。
- **自动跟随保证**：缩放只存在于 adapter.js（小游戏独有文件），网页版 js/ 一行不改；
  未来网页版更新素材/玩法/机制 → sync-minigame.sh 照跑 → 手机端自动继承桌面比例。
  v3 需要的 transform 新增规则数 = 0（v2 需要 10+ 条，每条都是未来同步的断锚点）。

**实施清单（确认后执行）**：
1. adapter.js：视口固定 + 触摸映射 + 胶囊映射（~30 行）
2. ui.js：首页内容宽钳制 min(vw,1280) + HUD 安全区（~10 行，可选）
3. 验收：DevTools 874×402 视口（布局）→ 170% 缩放（角尺寸可读性）→ 真机预览

**为何放弃 v2（F=0.70 逐元素缩放）**：v2 要给十几个字号逐条加因子——每条都是未来同步的
断锚点；且竞品对比实测"角色大小已在档内"，需缩的只有文字与面板，视口级一刀切更稳、
更符合"自动跟随"约束。

### v2 归档（被 v3 取代，仅存档）

全局缩放因子方案：

物理对照（iPhone 16 Pro 横屏全屏 14.54×6.69cm，1pt=0.166mm；桌面 2K27" 全屏 59.8×33.6cm，1px=0.233mm）：

| 元素 | 竞品实测 | 我们现状(手机) | 结论 |
|---|---|---|---|
| 玩家 | 3.8-5.3mm | 96×0.35=5.6mm | ✅ 在档，**zoom 维持 0.35**（0.32 可微调） |
| 敌人 | 4.2-5.7mm | 64×0.35=3.7mm | ✅ 在档（略小，zoom 0.38 可到 4.0mm） |
| 计时器 | 3.7-4.2mm | 34pt=5.7mm | ❌ 偏大 ~1.4x |
| 伤害飘字 | 1.7-2.2mm | 15pt=2.5mm | ❌ 偏大 ~1.4x |

**v2 结论：世界 zoom 不动（0.35，角色/视野与竞品同档）；只缩"文字与固定 px 的面板/瓦片"。**

```
F = clamp(短边pt / 720, 0.70, 1.0)     // 手机 ≈ 0.70，桌面 = 1（首推此因子）
// 用途：HUD 字号、地图瓦片 92×69、首页固定尺寸块 全部 ×F
// zoom 保持 0.35（如需角色更小巧可 0.32，竞品区间 0.32~0.40）
```

（v1 的"zoom 下限 0.20~0.25"按桌面比例推算，会把角色缩到 3~4mm，小于竞品区间，作废。）

### 4.2 字号规格表（F=0.70 时的手机实际值）

| 元素 | 现值(720p px) | ×F 后手机实际 | 换算 mm | 竞品区间 mm |
|---|---|---|---|---|
| HUD 计时器 | 34 固定 | ≈24pt | 4.0mm | 3.7-4.2 ✔ |
| HUD 击杀/金币 | 18 固定 | ≈13pt | 2.2mm | 2.0-2.3 ✔ |
| 波次/地图名 | 15 固定 | ≈11pt（下限） | 1.8mm | ✔ |
| 伤害飘字/暴击 | 15/22 固定 | 11/15pt | 1.8/2.5mm | 1.7-2.2 ✔ |
| Boss 名条 | 15 固定 | ≈11pt | 1.8mm | ✔ |
| 主菜单标题 | vh×0.13 | 不变（比例守恒） | 8.7mm | — |
| 按钮 | bh=max(32,9%vh) | 高 ≥44pt（触控红线），字 16pt | 7.3mm | — |

红线：文字 <11pt 取 11pt；触控热区 <44pt 取 44pt。桌面（F=1）维持现值不动。

### 4.3 首页布局（874×402 目标版式）

- 四块改为**锚点 + S 缩放**：标题(顶部中央, y=8%h)、猫(左下, 高=45%h)、
  地图格(右下, 瓦片×S、距底 12%h)、按钮组(底部中央, 高 44pt×S)。
- 地图格 3 列总宽 52×3+18×2 ≈ 192pt，右锚点留 24pt 边距，不会再越界。

### 4.4 安全区

- 顶部 HUD 右上角按钮组下移到胶囊下方：`wx.getMenuButtonBoundingClientRect().bottom + 8`。
- 左右各留 safeArea 边距（刘海横屏时两侧 ~44pt）。

### 4.5 验收矩阵（桌面测试方法学）

物理换算：iPhone16Pro 横屏 1pt=0.166mm@持机25cm → 角尺寸 ≈2.3 角分/pt；
2K27" 桌面 1px=0.233mm@坐姿60cm → 角尺寸 ≈1.3 角分/px。**同一 pt 在桌面上比手机上看小 ~1.7 倍。**

| 视口 | 验什么 | 说明 |
|---|---|---|
| A. DevTools 自定义 874×402 | **布局**：首页四块不重叠、瓦片/按钮位置、胶囊避让 | CSS 像素级精确，布局真值 |
| B. A 基础上 Chrome 缩放 **170%** | **可读性**（角尺寸与真机一致） | 170% = (60cm/25cm)×(0.166/0.233)，桌面看起来的大小≈真机 |
| C. 1280×720 窗口 + 2560×1440 全屏 | **桌面回归**（F=1 分支，H5 玩家） | 现版观感不变 |
| D. IDE 机型选 iPhone 16 Pro（自动横屏） | 综合观感 + 真机预览扫码 | 最终确认 |

口径：A 里"文字能读清" = 真机上更清楚（桌面角尺寸偏小是保守测试）；
B 里觉得"太大"才是真太大。可读性本身由规格表的物理毫米值保证，A/B 是人眼复核。
